# Mordheim Project

Mordheim Chronicler: a campaign manager for the Mordheim tabletop game. Django + DRF backend (`backend/`), React + Vite + TypeScript frontend (`frontend/`).

**Production:** backend on Render (Starter, Frankfurt), Postgres on Neon (Frankfurt, beside Render since 3 Nov 2026; it was London), frontend on Vercel. Every SQL query is still a network round trip, so **query count is latency**. Prod's IDs, the wipe procedure and deploy checks are in **`docs/working-notes.md`**, with William's other standing decisions (the database is ours to wipe, the content plan, the open items).

## Product principles (from William)

- **A guide, not a gatekeeper.** The tabletop rules and house rules change all the time, so the app warns ("above race maximum", "warband over size") and lets the player continue. Add a hard block only where William has asked for one (today: the hero and hired-sword caps when adding new units directly). When unsure, warn and allow, and ask before blocking.
- **Soft delete** records (dead and dismissed units, etc.) rather than deleting rows.
- **Don't preserve old-campaign quirks** when a rule changes, unless William says otherwise.
- **Lossy actions say so plainly** (e.g. "all carried items are lost; move them to the stash first").
- **No fluff text** (William, 1 Nov 2026). Don't add helper sentences that explain what the page already shows or how a control works ("The rest stay listed, greyed out", "every setting at or below it"). A line earns its place only if the player would otherwise get something wrong: a warning, a lossy action, a number they need. When in doubt, leave it out.
- **Not allowed right now means greyed out, still clickable,** with a warning when picked (17 Oct 2026). A warband's tailored lists are guidance enough; don't police the general pickers (5 Nov 2026).
- **Every roll can be typed in** (5 Nov 2026: "this is the entire vibe of the app"): any dice the app rolls also takes the number rolled at the table.
- **Edge cases are rule text, not code** (4 Nov 2026): a narrow book case (a promotion, a one-off timing) is a warband rule the player reads, not automation or a to-do.
- **A form with more than 8 inputs asks "Discard changes?"** before closing with unsaved edits; short forms don't (5 Nov 2026).
- **Gold rounds up** (6 Nov 2026: "always round up in mordheim for gold"): half of 35 gc is 18, for any halved or divided gold (`(value + 1) // 2`, as `apps/warbands/services/prices.py` does).
- **Skills and items match ours by name and effect** (6 Nov 2026): an import links ours only when both match. The same effect under another name stays separate and becomes a question for William. A limit on who in a warband may take a skill opens the skill's description, or sits in its group's note for a skill of ours; never in a warband rule.
- **Start afresh** (30 Oct 2026: "easier to start afresh"): when new code replaces old, delete the old component, its tests and dead helpers in the same change, with no shims, wrappers, re-exports or aliases.

## Engineering rules (must follow)

The full rules and the definition of done are in **`docs/ENGINEERING_RULES.md`**. Read it before changing code. The review findings and the improvement plan are in `docs/review/` (start with `docs/review/PLAN.md`). The non-negotiables:

- **The server owns business rules** (costs, XP thresholds, level-ups, permissions, battle outcomes). The frontend displays them and never re-implements them.
- **Query budgets.** Every list or detail endpoint uses `select_related` / `prefetch_related`, runs no queries in loops, and has an `assertNumQueries` test. The query count must not grow with row count.
- **Thin views, logic in services** (`apps/<app>/services/`). Serializers don't run un-prefetched queries.
- **Gold, stock and XP change atomically** (`F()` or `select_for_update` inside `transaction.atomic`). Every gold change writes its ledger row in the same transaction. One-shot actions (finalise battle, complete trade, level-up) are idempotent.
- **Permissions are enforced server-side on every endpoint.** The API returns capability flags (`can_edit`, ...) and the UI never shows an action the server will reject.
- **Never block a response on Pusher or Resend.** Dispatch on commit, in the background, with short timeouts. Realtime events carry the change, not a "refetch everything" ping.
- **Heroes, henchmen and hired swords share code.** Express their differences as configuration, never copy-paste. Backend: `apps/warbands/units/` (registry `kinds.py`, behaviour differences in `hooks.py`, shared `services/`, generic views on `WarbandScopedView`); visible units go through `on_roster()` / `kind.visible()` only. Frontend: one card for every kind (`features/warbands/components/roster/UnitCard`, its kind read from `unit-view.ts`), the unit API in `features/warbands/units/`, and one sheet query (`useWarbandSheet`) gated by its `capabilities`.
- **Frontend server state uses TanStack Query.** No ad-hoc `fetch` in `useEffect`, no server data copied into global context, and mutations invalidate only the affected query keys. Global context holds only small, rarely-changing app state.
- **Size limits:** backend files ≤ 400 lines and functions ≤ 60; frontend route files and components ≤ 250 lines. Split anything bigger by concern.
- **Every bug fix ships with a test that fails before the fix.** Frontend tests sit next to the code (no duplicate `__tests__/` copies).
- **Refactors and behaviour changes never share a PR.**
- **Green on every commit:** backend tests + ruff + ruff format + mypy; frontend `vitest run` + `tsc --noEmit`.

## Current gotchas

- Backend tests run through `config.test_runner.NoNetworkTestRunner`. It blanks the Resend and Pusher credentials and raises `ExternalNetworkCallError` on any non-loopback connection, so mock external services in tests; never re-enable them.
- Local realtime runs through **soketi** (a Pusher-compatible server in `docker-compose.yml`, port 6001). Compose overrides the `PUSHER_*` / `VITE_PUSHER_*` values from the `.env` files, which still hold production Pusher credentials, so never run the backend or Vite outside compose with those `.env` values. (A cloud session writes its own `backend/.env` with no keys: see "Cloud sessions".)
- Vite doesn't typecheck on build; `npm run typecheck` (and CI) does.
- **Data is disposable during the review** (William, 2026-10-18): local and production databases may be wiped and reseeded with `manage.py seed_all`, so don't write backfills or data repairs. Every migration must still run on an empty database. A wiped production database reseeds itself: gunicorn's `when_ready` hook starts `manage.py seed_catalogue_if_empty` in the background, which runs `seed_all` until a book hired sword (seeded last) exists.
- **Migrations were reset to a fresh `0001` per app in the bestiary rewrite** (150 files became 21; battles, bestiary and campaigns split into `0001` + `0002` over foreign-key cycles). A database migrated before the reset must be wiped (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;` plus the grants) before it migrates again, because its `django_migrations` rows clash with the new names. Three hand-written migrations hold what an empty database still needs: `campaigns/0003_seed_roles_and_permissions` (a frozen copy of `campaigns/constants.py`; a new code needs a new data migration), `core/0002_catalogue_version_row` and `battles/0003_battle_event_kill_killer_index` (raw SQL the models don't declare).
- **Gold and stash changes go through the services**: `apps/warbands/services/ledger.py` (`record`, which writes the signed row and moves the stored `Warband.gold`; `manage.py check_gold` compares the two) and `apps/warbands/services/stash.py`. Purchases are one `POST warbands/<id>/purchases/`; warnings (overspend, a spent trading action, a failed rarity roll) are returned, never refused.
- **Campaign access goes through `CampaignScopedView` and `apps/campaigns/access.py`** (one named rule per endpoint, deny by default). The campaign detail's `capabilities` are what the UI gates on: frontend campaign screens read `features/campaigns/capabilities.ts`, and a lint rule makes a `campaign.role` check an error. An **archived campaign is read-only everywhere** (campaign routes, warbands, battles, trades, the custom catalogue, joining): writes answer 403 `campaign_archived` unless the view lists the method in `allow_archived`. Campaign-wide changes ride `private-campaign-{id}-events` (`campaign.updated`; `warband.changed {warband_id}`, sent after commit by every `WarbandScopedView` write that succeeds (`announce_change()`, once per request), by finalise, an approved reported result and a completed trade, and skipping the writer's socket (every warband write sends `X-Pusher-Socket-Id`), makes other members' open pages of that warband read it again; `encampments.changed`, the Encampments page reading its list again); changes for one member go to their `private-user-{id}-notifications` channel.
- **The catalogue framework is `apps/core/catalogue/`**: the kinds registry (`kinds.py`), the generic views and one write path, versions and Revert (a campaign's version replaces a book entry through `replaces`, never the name; find the current entry with `current.py`, move copies with `remap.py`), archive and removal (`archive.py`) and the badge fields. Lists are cached per kind, campaign, catalogue version and query, so **any code that writes catalogue rows must call `core.catalogue.cache.bump`** (it also sends `catalogue.changed`). The list cache is off in tests unless a test turns it on (`catalogue_cache_on()`).
- **Settings and grades (grading phase 1)**: only settings carry a grade (`CampaignType`: `grade`, `sort_order`, `always_on`; Mordheim is split into Mordheim 1a, 1b, 1c, 2a and Grade 3). A campaign stores the settings it ticked (`Campaign.campaign_types`); picking a grade is a preset. `apps/campaigns/in_play.py` holds the visibility rule: an entry is in play when its setting is ticked or always on, or it has none (custom entries; rows not graded yet count as Mordheim's). Catalogue lists read for a campaign carry `setting_id` and `in_play`. The reference pages and Search everything list only what is in play (William, 1 Nov 2026: `features/reference/in-play.ts`; their Setting filter offers Mordheim 1a to 2a as one "Mordheim"); the store, the hire picker, the level-up pickers and the warband type picker grey the rest with a warning. A reference page's filters are dropdowns on one line under the search, never chips (William, 26 Nov 2026: `features/reference/FilterLine.tsx`): its type (Wargear's Type, Specials' Category, Scenarios' Players, Rules' Section), then the Setting. Its orders are `?sort=` (`list-sort.ts`, each direction that matters an order of its own: "Cost: low to high"): the web sorts from its column headings, and a phone from one arrows button (`SortMenu`) at the line's right edge that never reads as a filter (William, 24 Nov 2026), shown only where the list has more than one order. No page sorts by setting (William: "Don't need a setting sort on anything"): Wargear by name, cost and rarity, Specials by name and kind, the Bestiary by name, cost and kind, Hired swords by name, hire fee, upkeep and rating, Dramatis personae by name, hire fee and upkeep, Scenarios by name, weight and source; Skills, Spells and Warbands by name only. A warband has a `warband_type` (and `counts_as`); warband types and groups live in `apps/warbands/models/types.py`. `seed_settings`, `seed_warband_types` and the item, skill and hired-sword seeders read `backend/catalogue_import/out/` in place (rebuild it with `python -I catalogue_import/build.py`).
- **Campaign presets** (William, 17 Nov 2026; `apps/campaign_presets/`): a campaign makes two choices. Its preset is the published campaign it plays (`Campaign.preset`, null for none), which dictates the *rules*; the content in play stays the owner's, because "content is different to rules". A preset is data (`catalogue_import/sources/campaign-presets/*.json`, its README the shape, seeded by `seed_campaign_presets` in `seed_all` after the settings and the charts): the settings it guides towards (by name), the structural settings it dictates (`exploration_chart` by slug, `enable_locations`, `enable_encampments`, `enable_campaign_points`, `enable_blood_pacts`, `max_heroes`, `hero_death_roll`) and a `rules` file in `sources/campaign-rules/` holding its `rules`, `battle_rules` and `charts` (that README too). **A field left out is a field it says nothing about** (Mordheim's preset dictates nothing; Marienburg's dictates the Wasteland chart, the three pages, blood pacts, 6 heroes, D66, its 55 rules and its 21 charts), and a preset naming a setting, chart or rules file we don't hold is skipped with a warning, never seeded half-built. A rules file's `encampment_rules` and `encampment_groups` are the Encampments page's (see Encampments). A rules file's `warband_rules` (William, 23 Nov 2026: `CampaignPresetWarbandRule`, `{title, text, groups, types}` by group name and type slug) are a setting's rules for one race's warbands or one type's, Karak Azgal's Dwarf drunks: a warband raised in a campaign playing the preset gets those for its own type or a group holding it (never one it counts as) among its own rules after its template's, template or none (`campaign_presets/services/warband_rules.py`), and Add missing rules brings them to one raised before. `GET campaign-presets/` is the dropdown and `GET campaigns/<id>/preset/` says what the preset `sets` and the campaign's `departures` from it; **the server words every line** (`wording.py`), and a preset-set control is greyed, still operable, and warns when departed from (`PresetNote`, `presetDim`).
- **Campaign rules, battle rules and charts** (William, 19 Nov 2026; `apps/campaigns/models/content.py`, `models/charts.py`): a campaign's rules and its battle rules are **one table** (`CampaignRule`) told apart by `kind` (`campaign`, `battle`; a third, `encampment`, is the Encampments page's), because they are the same thing to write, read, order and copy; a battle rule only matters while a game is being set up or played (the weather, the ground, an encounter being triggered). Both carry an `umbrella`, the heading clearly related rules share ("one modal for all shared rules"): blank stands alone. **Umbrella a setting's rules as you import it** (William, 20 Nov 2026), campaign rules as much as battle rules, which were grouped first: a run of rules on one subject becomes one row, so Marienburg's 17 campaign rules read as 9 and Khemri's 9 as 3. The names that recur are **Campaign points and plots** (the six that open Marienburg and Border Town Burning alike: the points, choosing and changing a plot, points once lost, winning, starting over), **Captives**, **Trade**, **Cargo**, **Water**, **Locales**, **Weather**, **Fire**, **Territories**, **Boats** and **Random events**. That is the exploration chart's shape, not a grid of cells, because the books' tables are mostly prose; a nested sub-table of two or three lines rides inside its row's text. Nothing is applied, rolled or logged: a chart is read, as a rule is. `campaigns/<id>/campaign-charts/` is the CRUD (`manage_campaign_rules`, a chart written whole with its results), and the presets carry both (`CampaignPresetChart`). Frontend: one page of three lists (`features/rules/routes/CampaignRules.tsx`, the rows from `campaign-rule-rows.ts`), each row opening **its own modal**; the campaign page links to that page rather than showing the rules (`CampaignRulesLink`), and the battle's Rules sheet gains Battle rules and Charts chips.

- **Items and who can buy, hire and learn (the items rebuild)**: an item's rules are `ItemRuleLink` rows (a shared `ItemRule` by slug, worded the item's own way only where it differs, or a rule of its own) with D6 tables as `{columns, rows}`, placed in the text by `{{table:N}}`; its prices are `ItemAvailability` rows (cost, dice and multiplier, cost note, label, rarity with null as Common, a note shown when buying). - **Henchmen loadouts**: a henchmen group's item rows (`HenchmenGroupItem`) are what every member carries, one copy each, and a `HenchmanItemGap` (member, row, reason `short`/`lost`/`used`/`kit_taken`, `left`) records a member who lacks one; a row's copies are its living members less those gaps. `apps/warbands/services/loadouts.py` holds the rule: a group takes copies as one row (a purchase buys one for each living member; copies moved in arm the oldest members and gap the rest) and gives up a whole row (moves, sales), and `units/services/members.py` does a member's part (a recruit's kit from the stash or without, a dismissed member's share to the stash or with him, "Take his kit", filling or leaving a gap: `gaps/<gap>/`, `members/<member>/take-kit/`). Nothing matches copies to members by row order any more: in battle each member carries the rows he has no gap on (and rides the group's mount only then), a dead member deletes nothing, a lost horse or used item is a gap, and a member whose kit was taken is left out of prebattle at first (`outReason`). Missing games are a member's own (William, 25 Nov 2026: `Henchman.missing_games`, set beside Dismiss in the group's edit form; a group has none): he stays in the group's size, leaves the rating and prebattle's first pick, and finalise counts his games off. - **Fees and skill lists**: a hired sword's, dramatis persona's and warband hireling's `hire_fee` and `upkeep_fee` are each one JSON fee (`apps/hirelings/fees.py`: `kind` gold, replaces_hero, special or none; `gold`; `dice` and `dice_multiplier`; `{resource, amount}` lines; a `note`), read from mordheimer by `catalogue_import/fees.py`. - **Installable app** (William, 25 Nov 2026: "installable as a pwa on android and on apple phones"): `public/manifest.webmanifest` (standalone, the wyrdstone shard icons 192/512 and a maskable 512) and the iPhone tags in `index.html` (`viewport-fit=cover`, so the top bars' `env(safe-area-inset-top)` padding works under the notch). **The keyboard shrinks the screen** (William, 26 Nov 2026): the viewport's `interactive-widget=resizes-content` makes Android Chrome resize the page, and iOS Safari, which ignores it, has `lib/use-keyboard-frame.ts` sit `BottomSheet` and a phone's `DialogContent` on its keyboard, as tall as what it leaves, the focused field scrolled back into view. No service worker: Android installs without one, and none means no stale deploys. Its light and dark shade: the browser bar's `theme-color` and an iPhone's `apple-mobile-web-app-status-bar-style` follow the theme (`lib/theme.ts`, `public/theme-init.js`; an iPhone reads its bar at launch). `lib/install.ts` keeps Android's install prompt for Account → Appearance's Install button, and tells an iPhone in Safari "Share, then Add to Home Screen".
- **Production startup guards** (`DJANGO_DEBUG` off): `DJANGO_SECRET_KEY` must be 50+ characters; `RATE_LIMIT_NUM_PROXIES` defaults to 1 (Render's proxy) with a warning, and a value that isn't a whole number stops startup; with `RESEND_API_KEY` or an SSO provider's pair set, `FRONTEND_URL` (https) must be real, and with `RESEND_API_KEY` set `DEFAULT_FROM_EMAIL` must be real too (not at example.com, and not Resend's shared `resend.dev` sender, which delivers only to the Resend account's owner). `manage.py` hides these messages behind `AppRegistryNotReady`; gunicorn shows them.
- **Social sign-in** (`apps/users/sso/`, `services/sso.py` and `sso_accounts.py`): Google and Discord through one
  registry (a module per provider; a third is a module and a row). OAuth 2.0 code flow with PKCE, the code exchanged
  **server-side** (`sso/client.py`, the only module that touches the network, so tests mock one place), so no client
  secret or id is in the bundle and no browser-minted token is trusted; neither provider's ID token is read at all,
  the profile comes from its own userinfo endpoint. `GET auth/sso/<provider>/start/` writes an `SsoLoginAttempt`
  (state, PKCE verifier, and the SHA-256 of a secret the browser keeps in sessionStorage, ten minutes, single use)
  and answers the authorize URL; the provider returns to the **frontend** (`/auth/callback/<provider>`, built from
  `FRONTEND_URL`, which production refuses to start without once a provider's credentials are set), which posts
  the code to `POST auth/sso/<provider>/callback/`. Tokens are minted by the password path's `accounts.sign_in`, so the session
  key and sign-out-others work unchanged. A `SocialIdentity` row per `(provider, subject)` means several providers on
  one account. **Who it reaches**: the linked identity, else an active account matching a **verified** email
  (username or email), else a new account with an opaque `sso-<random>` username (never from the address) and no
  usable password; an unverified email never matches, and its address is kept on the identity row only. A deleted
  (inactive) account is never matched or resurrected, and deletion unlinks its providers. **One account per address,
  and only SSO may combine** (William, 19 Nov 2026: "lets combine if someone's account is the same email as their
  Google or discord"): a verified email proves the person controls it, so SSO onto a password account links (and **ends its password
  and every session**, because registering never proved the address: William, 21 Nov 2026; the callback answers a
  `notice` in the server's words, shown once, and Forgot password sets one again), but
  typing an address into the register form proves nothing, so registration never attaches to an SSO account. It
  refuses, naming the provider(s) that account has (`serializers.email_taken_message`), matching every active
  account's `email` and not just the usernames, with `users/0003`'s partial unique index on `LOWER(email)` where
  `is_active AND email <> ''` behind it (so a race is refused too, caught as BUG-84's already is, and the accounts
  that keep no address — deleted, and an unverified-email SSO one — collide with nothing). **Forgot password is for
  password accounts only** (William, 19 Nov 2026): a reset looks up `username=email`, which an SSO account's opaque
  username never matches, so a request for its address sends nothing and gives the same generic answer as an unknown
  one; a password account that later linked a provider keeps its reset. There is no "add a password" flow. **No refusal is ever a
  401** (400, 403 or 503 with a code: `sso_invalid_state`, `sso_not_configured`, ...), because the frontend signs out
  on a 401. A provider with either credential unset is left out of `GET auth/sso/providers/`, which is what the
  sign-in card's buttons read. The CSP needs nothing: the trip to the provider is a top-level navigation, the marks
  are inline SVG, and no provider script or iframe is used.
- **Sessions:** every token carries the user's session key (`UserAccount.session_key`, claim `sk`). A reset, a password change or sign-out-others sets a new one, and old tokens get 401 `session_ended`. **A 401 only ever means "not authenticated"** (a wrong current password is a 400), because the frontend signs out on a 401 after a refresh. Frontend: `lib/session.ts` owns the tokens and the cached user; nothing else writes them. An answer that lands after the session has moved on (signed out, another account) is ignored: `profileLoaded(token, user)` checks `session.isFor(token)`, and `updateUser` takes only the signed-in user (BUG-170).
- **A deleted account stays as a user row** (`apps/users/services/deletion.py`, AUTH-NEW-05): first name "Former player", username `deleted-<id>`, no email, an unusable password, inactive, so its warbands (and the encampments they hold), battles and ledger keep their owner as retired records. `display_name` already shows "Former player"; anything new that lists, counts or emails users must skip inactive ones.

## Cloud sessions

A Claude Code cloud session (claude.ai/code, the Claude app) is a fresh clone on an Ubuntu 24.04 VM. Nothing outside git is there: no real `.env`, no PDFs, no memory notes (William's standing decisions are in `docs/working-notes.md`). The rules for William's PC don't apply in the VM: run uv, python and npm natively.

- **Getting ready:** the environment's setup script runs `bash scripts/cloud/setup.sh` as root before Claude starts, and its disk is cached for about a week: poppler-utils and tesseract-ocr, `backend/.venv` (uv, Python 3.12), `frontend/node_modules` (npm ci) and a migrated empty database. Then every session the SessionStart hook in `.claude/settings.json` runs `scripts/cloud/session-start.sh`, which does nothing unless `CLAUDE_CODE_REMOTE=true`: it starts Postgres 16, makes the role (`postgres`/`postgres`) and database `mordheim` if missing, writes a throwaway `backend/.env` if there is none (DEBUG on, no Resend or Pusher keys, so no email and no realtime), installs whatever packages the checkout lacks, and migrates. It never fails the session; its log is `/tmp/mordheim-session-start-<checkout>.log`.
- **Seeding** is a step of its own (about 20 seconds): `cd backend && uv run python manage.py seed_all`, then `uv run python manage.py seed_demo_campaign` (sign in as `captain@mordheim.test`, password `password`).
- **Gates:** `bash scripts/cloud/gate-backend.sh` (tests, ruff check, ruff format --check, mypy, `makemigrations --check`, `check --deploy`; about 13 minutes). It runs them on **production's settings** (`DJANGO_DEBUG=0` and a long key, exported so they win over `backend/.env`), because CI does: a gate on DEBUG-on settings passes where CI fails, which is how a test that only holds with the browsable API installed left main red for two days. And `bash scripts/cloud/gate-frontend.sh` (typecheck, lint, format:check, build, vitest; about 2.5 minutes). Each prints its steps' last lines and exits non-zero on a failure; full logs are in `/tmp/mordheim-gate-<checkout>/`. `GATE_PARALLEL=auto` runs the backend tests on every CPU (about 3.5 minutes) and names a failure as a serial run does, since tblib sends its traceback back.
- **The end-to-end suite:** `bash scripts/cloud/e2e.sh` (Playwright, in `e2e/`, about 35 seconds). It starts Django and Vite itself, rebuilds the e2e campaign with `manage.py seed_e2e` and runs on one worker, because every test shares that campaign. It is not in either gate (it needs Postgres with the catalogue seeded). Realtime is not covered: soketi doesn't run in a cloud session.
- **The app for QA:** `bash scripts/cloud/dev.sh start` runs runserver on 127.0.0.1:8000 and Vite on :5173 (its `/api` proxy follows `API_PROXY_TARGET`); open `http://localhost:5173` in the session's Chrome. `dev.sh stop|status|logs`. Don't `docker compose up`: its Postgres would clash with the VM's on 5432.
- **Parallel agents:** `bash scripts/cloud/worktree.sh add <name> [<branch> [<base>]]` makes `.worktrees/<name>` with its own database `mordheim_<name>`, `.env`, packages and migrations. Run that worktree's own scripts (its `dev.sh` on other ports: `BACKEND_PORT=8001 FRONTEND_PORT=5174`); `worktree.sh remove <name>` drops it and its database.
- **The PDFs:** `bash tools/pdf-warbands/fetch.sh` downloads them (206 MB from www.broheim.net, which the environment must allow) and builds their text, measures and OCR in the git-ignored `.pdf-sources/`. Then follow `tools/pdf-warbands/PROCESS.md`.
- **Prod:** reading or wiping the Neon database takes the Neon connector, enabled on the session (its traffic goes through Anthropic, so no allowed domain is needed). Checking a deploy needs `mordheim-1.onrender.com` allowed; the Vercel status comes through `gh api` (GitHub's proxy). Rebuilding the live demo needs the prod connection string, which William keeps.

### Demo campaign

`docker compose exec backend python manage.py seed_demo_campaign` (re)builds the played demo campaign "The Shattered Crown" (DEBUG and a local database only): sign in as `captain@mordheim.test`, password `password`.

### Linting & Formatting

Uses **ruff** (config in `pyproject.toml`). Line length: 120.

```bash
uv run ruff check .        # lint
uv run ruff check --fix .  # lint with auto-fix
uv run ruff format .       # format
```

### Type Checking

Uses **mypy** with django-stubs (config in `pyproject.toml`). Requires `DJANGO_SETTINGS_MODULE` env var.

```bash
DJANGO_SETTINGS_MODULE=config.settings uv run mypy . --config-file pyproject.toml
```

### Pre-commit Requirements

Before committing backend changes, you MUST:

1. Run `uv run ruff check .` and ensure zero errors
2. Run `uv run ruff format --check .` and ensure all files are formatted
3. Run `DJANGO_SETTINGS_MODULE=config.settings uv run mypy . --config-file pyproject.toml` and ensure zero errors

Do not commit code that fails any of these checks.
